# Content Radar Discovery Intelligence Design

Date: 2026-09-03

## Goal

Extend the simplified Content Radar with four tightly related capabilities without turning it back into a full production platform:

1. global search across the material already stored in Content Radar;
2. stronger Radar indicators that identify breakout content relative to each channel;
3. strict reference deduplication, especially for YouTube videos represented by different URL formats;
4. topic-aware discovery/classification that can recognize content such as Minecraft, SMP, roleplay, ARG, analog horror, series, and related niches even when those words are absent from the title or description.

The product boundary remains unchanged:

`find something useful -> save/transcribe it -> record a video idea -> manually use the material elsewhere`

This specification improves discovery and retrieval only. It does not reintroduce script generation, automated script comparison, production management, Canva workflows, publishing, or full video creation.

---

## Product Principles

### Keep discovery explainable

The Radar should expose understandable signals such as views/day, age, channel-relative performance, detected topic, and confidence. Avoid a mysterious AI-only score as the primary decision surface.

### Separate official metadata from Content Radar inference

YouTube data must remain distinguishable from classifications generated by Content Radar.

Example:

```text
YouTube category: Gaming
YouTube topics: Gaming, Role-playing video game

Content Radar topics:
- Minecraft
- Horror
- Roleplay
- Analog Horror
```

The system must never present inferred topics as if they were official YouTube metadata.

### Progressive enrichment

Cheap and reliable metadata should be used first. More expensive semantic classification should only be needed when simpler signals are insufficient or when a video is important enough to justify enrichment.

Preferred evidence order:

1. YouTube category;
2. YouTube topic details;
3. YouTube tags;
4. title;
5. description;
6. channel history/profile;
7. transcript;
8. optional semantic classifier for unresolved cases.

### Preserve source data

Raw YouTube tags, topics, category IDs, URLs, and metadata should be retained even if Content Radar later changes its classification algorithm.

# 1. Reference Deduplication

## Problem

A single YouTube video can be supplied through several URLs:

```text
https://www.youtube.com/watch?v=dQw4w9WgXcQ
https://youtu.be/dQw4w9WgXcQ
https://www.youtube.com/shorts/dQw4w9WgXcQ
https://www.youtube.com/embed/dQw4w9WgXcQ
```

These must resolve to the same reference.

## Canonical identity

For YouTube sources, the canonical identity is:

```text
source_type = youtube_video
youtube_video_id = <11-character YouTube ID>
```

The original submitted URL remains stored for provenance, but it is not the uniqueness key.

## Import behavior

When a YouTube URL is imported:

1. extract and normalize the YouTube video ID before creating a new source;
2. search for an existing reference using that ID;
3. if none exists, create the source normally;
4. if it exists and already has an active transcript, return the existing source instead of duplicating it;
5. if it exists but has no usable transcript, reuse the source and create/retry an import/transcription job;
6. repeated concurrent imports must not create duplicate rows.

## Database constraint

A database-level unique constraint/index should enforce uniqueness for YouTube video IDs rather than relying only on service-level checks.

Historical rows that already duplicate the same YouTube video require a safe migration/cleanup strategy before the constraint is enabled. The migration must not silently delete transcript data.

## Duplicate reconciliation

If duplicates already exist, choose one canonical source and re-associate dependent transcript/import metadata where practical. If automatic reconciliation could lose information, report the conflict instead of deleting records.

# 2. Official YouTube Discovery Metadata

## Data to collect

For YouTube videos, Content Radar should capture and persist when available:

```text
youtube_video_id
youtube_category_id
youtube_category_name
youtube_tags[]
youtube_topic_categories[]
channel_id
channel_title
```

Existing `raw_json` may retain the complete response, but frequently queried fields must not depend on repeatedly parsing a large raw JSON object.

## Category lookup

`categoryId` is stored as the official YouTube category identifier. The display name is resolved using YouTube video categories metadata for the relevant region when appropriate.

Category is deliberately broad. `Gaming` must not be treated as equivalent to `Minecraft`.

## Topic details

YouTube topic details should be normalized from the topic-category URLs/IDs returned by the API.

They are supporting evidence, not the complete Content Radar taxonomy.

## Tags

All returned YouTube tags should be preserved in normalized form for search/classification, while also preserving the original spelling where useful for display.

Common low-value tags must not automatically become user-facing autocomplete entries.

# 3. Content Radar Taxonomy

## Why a separate taxonomy is needed

Official YouTube categories are too broad for the intended use cases. Content Radar needs to distinguish concepts such as:

```text
Minecraft
Minecraft SMP
Minecraft Roleplay
Minecraft Horror
Analog Horror
ARG
Hardcore
Modded Minecraft
Lore
Series
Challenge
```

## Taxonomy entity

Use a normalized topic entity rather than a giant enum.

Each topic has:

```text
id
name
normalized_name
type
parent_id
status
created_at
updated_at
```

Supported topic types for this phase:

```text
topic
subtopic
format
series
```

Examples:

```text
Minecraft               type=topic
Minecraft Horror        type=subtopic, parent=Minecraft
SMP                      type=format
Roleplay                 type=format
Analog Horror            type=subtopic
ARG                      type=subtopic
Drathos SMP              type=series
```

A content item may have multiple topics simultaneously.

## Content-topic association

Each association stores:

```text
content_item_id
topic_id
confidence
source
signals_json
classifier_version
created_at
updated_at
```

`source` identifies the origin of the classification, for example:

```text
youtube_category
youtube_topic
youtube_tag
rules
channel_profile
transcript
semantic
manual
```

The same topic may be supported by several signals; the service should consolidate them into one current association while retaining explainability in `signals_json`.

## Confidence

Confidence is a normalized 0-1 value.

Examples shown to the user can use percentages:

```text
Minecraft — 96%
Analog Horror — 82%
```

Confidence must be used as a ranking/filtering aid, not presented as certainty.

# 4. Hybrid Topic Classification

## Recommended approach

Use a hybrid classifier.

### Stage A: deterministic/cheap signals

Evaluate:

- YouTube category;
- YouTube topics;
- tags;
- title;
- description;
- known term aliases;
- channel profile.

### Stage B: transcript enrichment

When a transcript exists, classify using its content as additional evidence.

Transcript evidence should be especially useful for videos with intentionally vague titles such as:

```text
We should never have opened that door
Something is watching us
This server was a mistake
```

### Stage C: semantic fallback

A semantic/LLM-style classifier is optional and should be invoked only when:

- deterministic evidence is ambiguous;
- the item is already high-value based on Radar signals;
- or the user explicitly requests deeper classification.

The system must work without Stage C.

## Rule vocabulary

Topic detection should support aliases and related terms.

Example Minecraft evidence may include terms such as:

```text
minecraft
creeper
nether
ender dragon
redstone
smp
survival
hardcore
modpack
forge
fabric
server
```

This vocabulary is configuration/data, not hard-coded throughout UI code.

## Negative evidence

The classifier should permit negative/contradictory signals to reduce false positives.

Example: a video discussing Minecraft only as a comparison inside an otherwise unrelated gaming video should not automatically become a high-confidence Minecraft item.

# 5. Channel Profiles

## Purpose

Channels provide context that titles and descriptions may omit.

If a channel overwhelmingly publishes Minecraft content, a vague new video from that channel should receive Minecraft evidence even before its transcript is available.

## Stored profile

Maintain a derived channel profile containing at least:

```text
channel_id
channel_title
sample_count
dominant_topics_json
recent_views_median
recent_views_per_day_median
recent_age_adjusted_samples
last_profiled_at
```

The profile is derived data and can be recomputed.

## Dominant topics

Dominant topics are calculated from recent classified videos from the channel.

The channel profile contributes evidence but must not blindly override a video's own metadata.

# 6. Better Radar Performance Indicators

## Problem with raw views

Raw views do not indicate how unusual a result is for the channel.

Examples:

```text
5M views on a channel that normally gets 6M = ordinary
700k views on a channel that normally gets 40k = major breakout
```

## Primary relative metric

Use channel-relative views/day:

```text
performance_ratio =
video_views_per_day / channel_recent_median_views_per_day
```

Use median rather than mean as the baseline because isolated viral videos distort a mean heavily.

## Minimum sample requirement

Do not show a precise relative multiplier when there is insufficient channel history.

Recommended states:

```text
samples >= 5       ratio available
samples 2-4        low-confidence estimate
samples < 2        insufficient history
```

Exact thresholds can be configuration constants.

## Radar display

A useful item should expose:

```text
1.8M views
+270k/day
6 days old
4.2x channel baseline
Minecraft · Analog Horror
```

Do not hide these behind one opaque score.

## Suggested breakout labels

Illustrative labels:

```text
< 0.75x       below usual
0.75-1.5x     normal
1.5-3x        above usual
3-7x          breakout
>= 7x         exceptional breakout
```

These labels are presentation aids and should remain configurable.

## Sorting/filtering

Radar filters/sorting should support at least:

```text
views
views_per_day
published_at
performance_ratio
topic
minimum topic confidence
```

Existing score can remain for compatibility but should not be the only discovery ranking.

# 7. Discovery Beyond Keyword Search

## Goal

A search configuration for `Minecraft` should be able to surface a Minecraft video even if the exact word is missing from title and description.

## Discovery sources

A search configuration may combine:

1. normal keyword searches;
2. YouTube official category filters;
3. YouTube topic filters where supported;
4. trending/popular video feeds where available;
5. known/relevant channel sampling;
6. post-collection Content Radar topic classification.

The important architectural distinction is:

```text
collection query != final topic classification
```

A video may be collected by a broad Gaming/trending query and later qualify for a Minecraft search because Content Radar classifies it as Minecraft.

## Search configuration evolution

Keep existing keyword support, but add structured topic criteria.

Conceptual fields:

```text
included_topic_ids[]
excluded_topic_ids[]
minimum_topic_confidence
minimum_performance_ratio
youtube_category_ids[]
```

Existing `youtube_categories_json` can be migrated/reused rather than replaced unnecessarily.

## Matching semantics

A content item matches a configured topic when its current topic association satisfies the configured minimum confidence.

Example:

```text
Search: Minecraft breakout
Topic: Minecraft
Confidence >= 0.70
Last: 7 days
Views >= 500000
Performance >= 2.0x
```

# 8. Series Detection

## Series is distinct from topic

`Minecraft` describes subject matter.

`SMP`, `Roleplay`, and `Series` describe format/subtype.

`Drathos SMP`, `Hermitcraft Season 12`, or another recurring named property is a series entity.

## Series signals

Use multiple signals:

- playlist membership/title;
- repeated proper names across channel videos;
- recurring title patterns;
- recurring tags;
- recurring description terms;
- recurring transcript entities;
- manual user assignment.

## Conservative creation

Do not create a new series topic from every repeated phrase.

Automatic series creation requires evidence across multiple videos, unless explicitly created/confirmed manually by the user.

## Series confidence

Series associations use the same confidence/explainability approach as other topics.

# 9. Discovery Terms and Autocomplete

## Goal

When configuring searches, autocomplete should provide structured suggestions instead of only arbitrary free text.

Example input:

```text
mine
```

Example suggestions:

```text
Topics
Minecraft
Minecraft Horror
Minecraft SMP
Minecraft Roleplay

Tags
minecraft hardcore
modded minecraft

YouTube Categories
Gaming

Series
<known matching series>
```

## Suggestion origins

Autocomplete can use:

- official YouTube categories;
- official YouTube topic metadata;
- Content Radar topics/subtopics/formats/series;
- promoted YouTube tags;
- previously used manual terms.

The UI must display the suggestion type/source.

## Tag promotion

All raw tags may be stored, but a tag becomes a user-facing suggestion only when it has enough signal.

Candidate promotion factors:

```text
number of distinct videos
number of distinct channels
recent usage
association with recognized topics
manual usage
```

Low-value generic tags such as `viral`, `youtube`, `video`, `funny`, and similar terms should be suppressible through a stoplist/relevance rule.

## Discovery term index

Maintain a query-friendly suggestion index, conceptually:

```text
discovery_terms
    normalized_term
    display_name
    type
    entity_id
    usage_count
    video_count
    channel_count
    relevance_score
    last_seen_at
```

This is derived/search data and can be rebuilt from canonical metadata.

# 10. Global Search

## Scope

Global search covers:

- Radar content items;
- Biblioteca reference sources;
- transcripts;
- lightweight ideas.

Topics and series may also appear as navigational suggestions, but the core result groups remain the four product surfaces above.

## Endpoint

Conceptual endpoint:

```text
GET /global-search?q=<query>&limit=<n>
```

Response groups:

```text
content_items
references
transcript_matches
ideas
```

## Transcript result

Transcript matches return enough context for immediate navigation:

```text
reference_source_id
transcript_id
segment_id
video_title
start_time
end_time
matched_excerpt
```

The frontend should open the corresponding reference detail and jump/scroll to the matching timestamp/segment where practical.

## Search implementation

Phase one uses PostgreSQL textual search/ILIKE/full-text capabilities already available to the project stack. Do not introduce vector embeddings for this feature unless later evidence shows normal search is insufficient.

## Ranking

Rank using straightforward factors:

- exact title match;
- prefix/title match;
- topic/name match;
- body/transcript occurrence;
- recency where useful.

The ranking formula should remain deterministic and testable.

# 11. Data Model Direction

The implementation plan may adjust exact table names, but the architecture should include equivalents of the following.

## `content_items` enrichment

Add or normalize frequently queried YouTube fields:

```text
youtube_video_id
youtube_category_id
youtube_category_name
youtube_tags_json
youtube_topics_json
topic_classification_version
performance_ratio
performance_baseline_samples
```

Some derived metrics may instead live in a dedicated metrics table if repository analysis shows that is cleaner.

## `reference_sources`

Add canonical YouTube identity if not already represented safely:

```text
youtube_video_id
```

Enforce unique identity for YouTube video references after safe historical reconciliation.

## `topics`

Canonical taxonomy entities.

## `content_item_topics`

Many-to-many topic associations with confidence and evidence.

## `channel_profiles`

Derived context and channel baseline statistics.

## `discovery_terms`

Derived autocomplete/search-suggestion index.

# 12. Processing Flow

## Ingestion/discovery

```text
collector finds video
        ↓
normalize YouTube identity
        ↓
store/update content item metadata
        ↓
collect category/tags/topicDetails
        ↓
cheap topic classifier
        ↓
update channel profile/baseline
        ↓
calculate Radar performance metrics
        ↓
if transcript later becomes available:
    enrich topic classification
        ↓
if still ambiguous and policy allows:
    optional semantic classification
```

## Reference import

```text
user imports URL
        ↓
extract YouTube ID
        ↓
lookup canonical reference
        ↓
existing?
  yes → return/reuse + transcribe if needed
  no  → create + import/transcribe
```

## Search configuration

```text
user selects topic/category/tag/series from autocomplete
        ↓
config stores structured filters
        ↓
collection uses broad relevant sources/queries
        ↓
post-collection classification decides final topic membership
```

# 13. API Surface

Exact routes may follow existing repository conventions, but intended capabilities include:

```text
GET /global-search
GET /topics
GET /discovery-terms/suggest
GET /youtube/categories
GET /content-items?topic_id=&min_topic_confidence=&min_performance_ratio=
GET /content-items/{id}/topics
POST/PATCH topic assignments only where manual control is needed
```

Existing reference import routes remain in place, with deduplication implemented transparently.

Avoid creating a large generic taxonomy administration interface during this phase.

# 14. Frontend Changes

## Radar

Add visible:

- age;
- views/day;
- channel performance ratio;
- detected top topics;
- confidence tooltip/details when requested.

Add filters/sorting for performance and topics.

## Search Configurations

Replace category/topic inputs with a structured autocomplete supporting:

- topic;
- subtopic;
- format;
- series;
- YouTube category;
- promoted tag.

Keep free-text keywords available because they remain useful for discovery.

## Biblioteca

No major workflow expansion. Deduplication should mostly be invisible, except duplicate imports can show a message such as:

```text
Este vídeo já estava na Biblioteca. Abrindo a referência existente.
```

## Global Search UI

Provide one global search entry point in the product shell/topbar.

Group results by surface and show transcript timestamps directly.

Do not add a separate heavy search workspace unless later usage proves necessary.

---

# 15. Error Handling and Edge Cases

## Missing tags/topicDetails

Classification proceeds with remaining signals. These fields are optional evidence.

## New channels with insufficient history

Display `Sem histórico suficiente` rather than inventing a performance multiplier.

## Deleted/private videos

Preserve existing stored metadata/reference where possible and mark availability state separately if needed.

## Duplicate race condition

The database unique constraint is the final authority. Service code must handle integrity conflicts by loading and returning the canonical existing row.

## Classification changes

When classifier rules/version change, associations can be recomputed. Store `classifier_version` so derived classifications are auditable.

## Conflicting classifications

Keep confidence/evidence. Do not force every item into one exclusive category; multiple topics are expected.

---

# 16. Testing Strategy

## Deduplication

Test all common URL forms resolve to one YouTube ID and one reference row.

Test concurrent/duplicate service paths against the unique constraint.

Test duplicate source with missing transcript triggers reuse rather than duplicate creation.

## Topic classification

Use deterministic fixtures covering:

- explicit Minecraft title;
- vague title + Minecraft tags;
- vague title + Minecraft-heavy channel;
- vague title + transcript evidence;
- analog horror / ARG evidence;
- conflicting evidence;
- unrelated Gaming video that must not become Minecraft.

## Performance

Test median baseline calculations and insufficient-sample behavior.

Test ratios with zero/missing views/day safely.

## Autocomplete

Test normalization, prefix matching, type grouping, tag promotion, and suppression of generic tags.

## Global search

Test grouped results and transcript match timestamps.

## Compatibility

Existing transcript fidelity tests and simplified Ideas/Radar tests must remain green.

---

# 17. Implementation Phases

## Phase 1 — Canonical reference identity and deduplication

Foundation for clean reference data.

## Phase 2 — Official YouTube metadata enrichment

Persist category, tags, topic details, and canonical video/channel IDs.

## Phase 3 — Channel profiles and relative Radar performance

Build median baselines and breakout indicators.

## Phase 4 — Taxonomy and hybrid topic classification

Add topic entities, associations, confidence, explainable evidence, transcript enrichment, and series foundations.

## Phase 5 — Discovery autocomplete and structured search criteria

Promote useful terms and let searches select topics/categories/tags/series.

## Phase 6 — Global search

Search across Radar, Biblioteca, transcripts, and Ideas with timestamp navigation.

Each phase should produce independently usable software and should not require later phases to keep the application functional.

---

# 18. Non-Goals

This design does not add:

- automated script comparison;
- script generation;
- automatic script writing;
- video production workflow management;
- thumbnail/music planning;
- Canva or whiteboard integration;
- collaborative editing;
- publishing automation;
- performance analytics for the user's own published videos;
- vector database infrastructure;
- mandatory semantic/LLM classification of every collected item.

---

# 19. Success Criteria

The architecture is successful when all of the following are true:

1. importing the same YouTube video through different URL formats never creates duplicate references;
2. the Radar can distinguish raw popularity from unusual performance relative to the channel;
3. a video can be classified as Minecraft or another topic without requiring that topic word in the title or description;
4. Content Radar distinguishes official YouTube metadata from inferred topics;
5. Minecraft subtypes such as SMP, roleplay, horror, ARG, lore, and named series can coexist as structured classifications;
6. search configuration autocomplete offers useful categories/topics/tags/series without flooding the user with raw tag spam;
7. topic-based searches can include videos found through broader discovery channels;
8. global search finds content, references, ideas, and exact transcript passages with timestamps;
9. the simplified Content Radar product boundary remains intact.
